# Wiki Schema Document

This schema governs how LLM agents and the `obsidian-kb-pipeline` pipeline read, write, and extend the Coding Knowledge wiki in your Obsidian vault.

## Page Types

| Type | Purpose | Naming Pattern | Folder |
|------|---------|----------------|--------|
| **entity** | A specific tool, API, service, or framework | `{service}-{topic}.md` | `APIs/` |
| **architecture** | How a system was designed and why | `arch-{project}.md` | `Architecture/` |
| **pattern** | Reusable technique across projects | `{domain}-patterns.md` | `Patterns/` |
| **gotcha** | Hard-won debugging knowledge, quirks | `gotcha-{tool}-{topic}.md` | `Gotchas/` |
| **workflow** | Step-by-step process for a recurring task | `workflow-{process}.md` | `Workflows/` |
| **comparison** | Side-by-side evaluation of alternatives | `compare-{a}-vs-{b}.md` | `Comparisons/` |
| **synthesis** | Cross-cutting insight from multiple sources | `synthesis-{theme}.md` | Root |

## Frontmatter Requirements

Every wiki page must include these fields:

```yaml
---
type: resource
tags:
  - wiki
  - {page-type}       # e.g., pattern, gotcha, entity
  - {domain-tags}      # e.g., n8n, supabase, gcp
status: reference      # or 'draft' for auto-generated pages needing review
created: YYYY-MM-DD
modified: YYYY-MM-DD
area: work
wiki-source: auto | manual | seed
wiki-confidence: high | medium | low
wiki-sources:
  - {source-id-1}     # Memory or session ID that contributed
---
```

### Wiki-Specific Fields

- **wiki-source**: Provenance of the page
  - `auto` — generated by the pipeline
  - `manual` — written by hand
  - `seed` — initial seed page, may be enriched by the pipeline
- **wiki-confidence**: How confident the extraction pipeline is in the content
  - `high` — from pre-distilled memory (pact-memory, agent-memory)
  - `medium` — from session extraction with clear context
  - `low` — from ambiguous sessions or cross-session inference
- **wiki-sources**: List of source identifiers that contributed to this page

## Content Guidelines

### What Makes a Good Wiki Page

- **Specific and actionable**: Include exact parameter names, code snippets, version numbers
- **Evidence-based**: Each claim should trace back to a real experience or source
- **Self-contained**: A reader should understand the page without reading all linked pages
- **Structured**: Use ## headings, bullet lists, and code blocks for scannability

### What NOT to Write

- Generic advice available in official documentation
- Opinions without evidence from real project experience
- Stale information that may have changed (mark with `(unverified)` if uncertain)
- Implementation details that belong in code comments, not a knowledge wiki

### Handling Uncertainty

- Mark uncertain claims with `(unverified)` suffix
- Set `wiki-confidence: low` in frontmatter
- Include the source context so a reader can verify

## Update Rules

### Additive Only

The pipeline never deletes existing content.  New extractions are integrated alongside existing material.  Manual edits are always preserved.

### Enrichment Flow

1. Pipeline reads existing page content
2. Deduplicates against what's already on the page
3. Adds new sections or appends to existing sections
4. Updates the `modified` date and `wiki-sources` list

### Conflict Resolution

If new extraction contradicts existing content:
- Keep both versions, clearly labeled
- Mark the conflict with `(conflicting — verify)` 
- Set `wiki-confidence: low` until manually resolved

## Cross-References

- Use `[[wikilinks]]` for all internal references
- Every page should have a `## Related` section at the bottom
- The MOC (`coding-knowledge-map.md`) indexes all pages by category

## Taxonomy

### Domain Tags (use in frontmatter `tags`)

| Tag | Covers |
|-----|--------|
| `n8n` | n8n workflow automation |
| `supabase` | Supabase, RLS, Edge Functions |
| `gcp` | Google Cloud Platform, GKE, CloudSQL |
| `nextjs` | Next.js framework |
| `react` | React patterns |
| `typescript` | TypeScript-specific patterns |
| `python` | Python patterns |
| `api` | API integration patterns |
| `auth` | Authentication and authorization |
| `security` | Security patterns and findings |
| `devops` | CI/CD, Docker, deployment |
| `database` | Schema design, migrations, queries |
| `mcp` | Model Context Protocol |

### Project Tags

Define your own project tags in `config/domains.yaml`. Example shape:

| Tag | Project |
|-----|---------|
| `frontend` | React/Vue/etc. frontend code |
| `api` | Third-party API integrations |
| `database` | Schema, migrations, queries |
| `devops` | CI/CD, infra, deployment |

The exact set is taxonomy — yours — not built-in.

## Index (MOC)

The `coding-knowledge-map.md` file is the Map of Content.  It is auto-updated by the pipeline after each run.  Format:

```markdown
## Section Name

- [[page-name]] -- One-line description
```

Manual entries in the MOC are preserved.  The pipeline only adds — never removes — entries.
